�使用“任意官网版请求”而不是当前内容来源

**位置**

- `backend/app/api/workspace.py:104-118`
- `backend/app/api/workspace.py:1192-1239`
- `backend/tests/test_api.py:503-556`

**问题**

`_message_uses_official_channel()` 只要找到一条 `ModelRequest.message_id == message.id` 且渠道类型为 `official` 的记录就返回 `True`。重新生成会复用同一条 assistant 消息并追加新的根 `ModelRequest`，所以该消息可以同时关联官网版和 Codex 请求。

复现顺序：

1. 使用官网版渠道生成同一 assistant 消息。
2. 选择 Codex 渠道重新生成，返回普通正文 `search("term")slow|this is documentation|1\n正文`。
3. 当前流式完成事件显示完整 Codex 正文。
4. 重新读取消息时，`_visible_message_content()` 因旧官网版请求而调用 `normalize_assistant_content()`，实际只返回 `正文`；JSON/TXT/Markdown 导出经过同一逻辑，也会得到被截断的内容。

补充临时回归测试已稳定失败，断言差异为：期望完整 Codex 正文，实际为 `正文`。现有 `test_codex_channel_preserves_search_like_normal_text` 只覆盖首次生成，没有覆盖同一消息跨渠道重新生成。

**影响**

- Codex 普通正文在刷新、复制（刷新后）和导出时被误清洗。
- 流式完成内容与消息 API/导出内容不一致。
- 首轮“渠道隔离”P1 仅在单请求场景关闭，多请求场景仍未关闭。

**修复建议**

1. 历史兼容清洗应绑定“当前消息内容的实际生成版本”，不要使用 `exists(any official request)`。
2. 最小修复可按根请求（`parent_request_id IS NULL`）选择实际产出当前内容的最新请求及其渠道；需同时定义失败、停止、幂等回放和重新生成回滚时的归属规则。
3. 更稳妥的实现是在消息或消息版本上持久化内容来源渠道/请求 ID，使内容与来源成为同一版本的不可歧义关系。
4. 增加官网版→Codex、Codex→官网版、重新生成失败/停止后的消息 API、三种导出和复制一致性测试。
