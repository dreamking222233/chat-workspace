## 已确认的实现

- `resolve_image_options()` 统一用于直接生成、编辑和文本工具调用；`16:9 2K 高清` 可解析为 `2560x1440/high`。
- 前端直接图片请求会先插入 `image_pending` 消息，文本工具的 `tool.started(generate_image)` 也会切换至相同卡片。
- 生成结果通过鉴权 Blob 加载，大图使用 `object-fit: contain`；`prefers-reduced-motion` 会停用点阵动画。
- 编辑调用会因携带参考图或遮罩图进入 Provider 的 `/images/edits` 路径。

## 首轮发现与修复

### P1：停止图片生成后，服务端仍可能写入迟到结果

**原问题**

前端停止按钮只中断浏览器 Fetch，直接图片生成没有在 Provider 返回后复核数据库状态，可能把已停止请求重新标记为 `completed` 并持久化图片。

**修复**

- 停止接口现在处理同一会话内全部运行中的根请求和子请求，并同步更新进程内取消标记与数据库 `stopped` 状态。
- 直接图片请求与文本工具图片请求保存结果前统一调用 `_claim_image_completion()`；该函数通过数据库行锁重新加载状态，使停止与完成的先后关系原子化。
- 若停止先发生，迟到的 Provider 字节被丢弃，不创建 Asset、不创建图片消息，也不回写 `completed`。
- 前端主动停止时保留用户提示词，仅清除乐观图片占位。
- 新增直接生图和文本工具生图的并发停止回归测试。

**结果：已解决。** 同步上游 HTTP 调用自身可能执行到返回，但其结果不会进入系统状态或资源存储。

### P1：接口允许 `n=1..4`，实际只保存第一张

**原问题**

Provider 解析器与聊天消息结构只持久化一个结果，允许 `n > 1` 会静默丢弃其余图片。

**修复**

- `SendMessageRequest` 与 `ImageGenerationRequest` 的公开合同固定为 `n=1`。
- `n > 1` 在 Pydantic/FastAPI 请求校验阶段返回 422。
- 文档明确说明后续开放多图需要同时实现结果列表、消息/资产持久化与前端画廊。

**结果：已解决。** 当前合同与实际单图能力一致。

### P2：`standard/hd` 会原样传给 `gpt-image-2`

**原问题**

方案声明 GPT Image 使用 `auto/low/medium/high`，但旧质量值可能未经转换进入 Provider。

**修复**

- 对外规范质量集合收敛为 `auto/low/medium/high`。
- 兼容旧客户端输入：`standard -> medium`、`hd -> high`。
- 原生 Function schema 只向文本模型暴露规范值。
- 单元测试覆盖请求 Schema、工具参数 Schema 与规范化函数。

**结果：已解决。** 旧值不会原样下传。

### P2：后端全量测试依赖开发机 MySQL

**原问题**

干净环境运行 API 测试会连接默认 MySQL，测试结果无法独立复现。

**修复**

- 新增 `backend/tests/conftest.py`，在应用模块导入前设置会话级临时 SQLite 和临时资源目录。
- 测试限流阈值单独提高，避免全量用例互相消耗开发配置配额。
- 环境变量使用 `setdefault`，显式指定的集成测试数据库仍可覆盖默认测试配置。

**结果：已解决。** 无本地 MySQL 时后端全量测试通过。
