# 全站移除模拟数据 Plan 评估

- 日期：20260902
- 评估对象：`./md/plan-全站-移除模拟数据-20260902.md` v1
- 评估方式：Codex 独立只读评估

## 评估结论

**v1 方向正确、技术可行，但暂不建议直接实施；需修订为 v2 后进入开发。**  
核心阻塞点是：页面 API 失败与空态未做到资源级区分、无渠道的数据库原子性边界需明确、测试环境隔离缺少强校验、历史测试数据尚无可证明的安全删除依据。

## 1. 方案完整性

建议补充一张“资源—状态—UI 行为”矩阵，至少覆盖 `/threads`、归档线程、`/projects`、`/models`、`/me/entitlement`：

- **成功且空**：显示对应空态。
- **加载中**：显示加载态。
- **请求失败**：显示错误态和重试，不得按空数据处理。
- `/threads` 失败时，不得渲染默认会话；移除 `activeThread` 的本地兜底对象。
- 归档、项目、模型加载失败应各自报错，不能因 `Promise.all` 任一失败而把其他成功数据一并清空。
- 无文本模型与模型接口加载失败必须区分：前者禁用发送并提示未配置，后者显示加载失败和重试。
- 删除、归档、恢复、重命名应以 API 成功后更新 UI，或保存完整快照并在失败时恢复；尤其当前删除/恢复路径不能继续 fire-and-forget。

还需明确持久化历史 `local-demo`、`local-*`、演示消息的处置范围。仅扫描源码和 `dist` 不足以保证真实 API 页面不会返回历史模拟记录。

## 2. 技术选型

现有 React Fetch/SSE、FastAPI、SQLAlchemy、pytest + provider monkeypatch 的组合适配本次改造，无需引入额外框架。

建议后端抽取统一的 `resolve_text_channel(...)`：

1. 解析请求模型、线程模型、指定渠道和默认真实渠道；
2. 校验渠道启用状态与文本能力；
3. 成功后才返回 `(model, channel)`；
4. 失败时在任何消息、`ModelRequest`、线程模型、回复内容修改前抛错。

状态码也应写入 API 契约：建议“指定渠道参数非法/不匹配”为 `422`，“模型存在但没有可用启用渠道”为 `503`，避免方案中把两类问题都定义为 `503`。

## 3. 后端无渠道原子性

当前改造目标可实现，但验收需扩大为：

- 发送无渠道：`503` 后 `Message`、`ModelRequest` 数量不变，`Thread.model` 与 `updated_at` 不变。
- 重新生成无渠道：`503` 后目标助手消息内容、后续消息、`ModelRequest`、线程字段均不变。
- 渠道解析必须发生在计算 sequence、创建占位消息、清空旧回复之前。
- 明确原子性仅覆盖本地数据库预检；渠道在预检后被禁用、或外部 Provider 运行中断，应走已有流失败协议，不应宣称该场景可回滚外部调用。

## 4. 测试数据库隔离

“无条件覆盖环境变量”是必要项，但还应补充：

- 在导入 `app.db.session`、`app.main` 前设置 `CHAT_DATABASE_URL`、`CHAT_STORAGE_DIR`、`CHAT_JWT_SECRET`、`CHAT_ENCRYPTION_KEY`，并清空 `CHAT_MODEL_CHANNELS_JSON`。
- 清理 `get_settings()` 缓存；启动测试后断言 `get_settings().database_url` 与 `engine.url` 都位于本次临时目录，否则立即失败。
- 测试之间重建隔离库或执行确定性清理，避免测试相互污染。
- 并行测试时每个 worker 使用独立临时目录和数据库。
- 增加回归断言：测试前后开发库连接信息和表计数均未被访问或改变。

## 5. 历史测试数据清理风险

这是当前方案风险最高部分。现有 `test-<uuid>@example.com`、固定显示名、测试密码等属于**候选特征**，并不单独构成可证明来源；仅凭邮箱域、前缀或名称自动删除仍可能误删真实数据。

建议调整为：

- 默认仅生成候选报告，不自动删除历史候选。
- `--apply` 必须提供经人工确认的主键 manifest、备份路径和目标数据库指纹；不接受宽泛筛选条件直接执行。
- 备份使用一致性数据库备份并包含资产目录；执行前校验备份可读取。
- 删除前输出关联闭包与各表影响计数，覆盖用户、线程、消息、请求、授权、刷新令牌、导出、资产、审计日志等关联数据。
- 无持久化 `test_run_id` 或其他可验证来源的遗留数据全部保留为“待人工确认”。
- 清理完成后增加数据库审计：统计 `local-demo` 线程/请求及演示消息残留，逐条决定清理、保留或人工迁移，避免真实 API 继续展示历史模拟内容。

完成上述修订后，方案可进入实施阶段。

## 6. v2 复核记录

第一次复核确认主体设计已落实，但要求继续补充：

1. 测试前后开发库连接指纹与业务表计数不变的自动验证。
2. 持久化 `local-*` 标记的扫描、计数与分类处置。

Plan v2 已补充隔离验证脚本/记录、开发库前后快照断言，以及 `local-demo` 和持久化 `local-*` 的联合审计范围。

### 最终复核结论

**通过。仍需修改项：无。**

资源状态边界、无渠道原子性、测试数据库隔离和历史数据安全审计均已落实到方案、文件/方法级 To-Do 与验收清单，可以进入实施阶段。
