# 图片生成参数与状态实施记录

## 任务概述

本次实现补齐了图片生成的两项体验：

1. 图片请求等待期间显示接近 ChatGPT 官网的“正在创建图片”圆角点阵卡片，完成后切换为大图、下载按钮和消息操作。
2. 直接生图、图片编辑以及文本模型触发的 `generate_image` 工具统一解析 Prompt 中的比例、分辨率和质量要求，并将有效参数下传到 OpenAI-compatible 图片接口。

## 核心代码说明

### 1. 确定性图片参数解析

`resolve_image_options(prompt, size, quality)` 会先标准化全角/半角和大小写，再识别：

- 比例：`1:1`、`2:3`、`3:2`、`3:4`、`4:3`、`9:16`、`16:9`。
- 方向：横屏、横版、竖屏、竖版、landscape、portrait。
- 分辨率：`720P`、`1080P`、`1K`、`2K`、`4K`。
- 质量：高清、高画质、高质量、low、medium、high 等。
- 显式尺寸：例如 `1920x1080`。

当前渠道预设中，`16:9 2K 高清` 会得到：

```json
{
  "size": "2560x1440",
  "quality": "high"
}
```

Prompt 的明确要求优先于接口默认值。无输出指令时保留请求方的 `size/quality`。

### 2. 统一调用链路

- `POST /api/v1/threads/{thread_id}/image-generations`
- `POST /api/v1/threads/{thread_id}/image-edits`
- 文本流中的原生 `generate_image` Function Calling
- 平台 `<platform_tool_call>` 兼容协议

以上四条路径都会在 `_invoke_image_provider` 前调用相同解析器，最终由 Provider 向
`/images/generations` 或 `/images/edits` 发送 `model`、`prompt`、`size`、`quality`、
`n` 和 `response_format`。

### 3. 图片生成状态

- 直接图片请求创建 `contentType=image_pending` 的本地助手占位消息。
- `tool.started(generate_image)` 会把文本流占位消息切换为图片生成卡片。
- `image.created` 到达后隐藏工具占位消息并加入真实图片消息。
- 工具后续如有文本说明，`message.delta/completed` 会把原占位消息恢复为普通文本。
- 请求失败和组件卸载继续使用原有清理逻辑；用户主动停止时保留用户提示词，只移除前端图片占位。
- 服务端停止接口会同时标记文本根请求和图片工具子请求；Provider 迟到结果在持久化前通过行锁复核，已停止时转为文本状态且不创建 Asset。

点阵卡片采用纯 CSS `radial-gradient + mask-image`，不增加图片资源；短视口会按
`100vh` 收缩，`prefers-reduced-motion` 下禁用呼吸动画。

### 4. 图片结果

- 结果预览最大宽度从 420px 增加到 680px。
- 使用 `object-fit: contain` 保持原始宽高比。
- 资产加载期间复用图片卡片状态。
- 下载按钮、复制、赞踩、分享和重新生成继续保留。

## 接口说明

图片请求继续兼容原合同，新增支持更多有界尺寸：

```json
{
  "prompt": "生成一张抖音直播间截图 16:9 2K 高清",
  "model": "gpt-image-2",
  "channel_id": "CHANNEL_ID",
  "size": "1024x1024",
  "quality": null,
  "n": 1,
  "response_format": "b64_json",
  "asset_ids": []
}
```

即使调用端使用默认尺寸，服务端也会根据 Prompt 将实际 Provider 参数解析为
`size=2560x1440`、`quality=high`。

当前消息合同只保存一张图片，因此 `n` 固定为 `1`，传入其他值返回 422。质量值统一为
`auto/low/medium/high`，旧客户端的 `standard/hd` 会在 Schema 中转换为
`medium/high`，不会原样传给 `gpt-image-2`。

## 测试验证

- 后端隔离 SQLite 全量：`51 passed`。
- 前端 Vitest：`6 passed`。
- TypeScript + Vite 生产构建：通过。
- Python `compileall`：通过。
- 本地浏览器确认：发送后立即出现“正在创建图片”点阵卡片及停止按钮。
- 真实 `gpt-image-2` 请求：上游约 31 秒返回 HTTP 200，页面成功切换到 16:9 图片、下载按钮和消息操作栏。
- 当前渠道源码与 OpenAPI 已核对：图片接口接收 `size/quality`，并把两者加入图片生成请求；渠道页面的 `16:9(2K)` 预设为 `2560x1440`。
- 并发停止回归：直接图片请求和文本工具图片请求在 Provider 返回前被停止后，请求保持 `stopped`，消息列表无图片，资产表无新增记录。

## 待优化项

- 当前接口明确限制单张主图；如后续开放 `n > 1`，需要同步实现 Provider 结果列表、消息/资产持久化和前端画廊。
- 当前渠道将尺寸作为生成提示传给上游模型，最终文件像素可能与请求值存在少量差异；本系统不做可能引入拉伸或裁切的强制后处理。

## 自行 Review 与修复

Review 首轮发现停止竞态、`n` 合同、旧质量值和测试环境四项问题，现已全部收敛：

1. 新增 `_claim_image_completion`，使用 `SELECT ... FOR UPDATE` 与持久化状态复核决定是否接收 Provider 结果。
2. 停止接口一次处理同一会话的所有运行中根/子请求；直接生图和工具生图均覆盖迟到结果测试。
3. 请求 Schema 固定 `n=1`；`standard/hd` 兼容输入转换为 `medium/high`，Function schema 仅声明规范值。
4. `backend/tests/conftest.py` 在应用导入前配置临时 SQLite、临时资源目录和测试用限流阈值，干净环境全量测试通过。
