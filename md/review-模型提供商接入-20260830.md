# 模型提供商接入方案评估

日期：2026-08-30
审查对象：`md/plan-模型提供商接入-20260830.md`

## 审查结论

方案方向合理，选择兼容聊天协议、SSE、multipart 和现有渠道优先级路由，能够覆盖目标能力；方案完整性尚不足以直接进入实施。核心问题集中在四个接口契约没有定稿：Base URL 与路径拼接、工具回合的消息持久化、图片编辑请求格式、模型同步的模型能力标注。

建议将方案修订为 v2 后再编码。若按当前版本实施，文本基础流可以落地，但工具调用、参考图编辑、断线恢复和历史消息重放会出现跨模块返工。

## 1. 方案完整性

### P0 必须补充

1. **数据库与迁移缺失**
   - 涉及文件清单没有 `backend/alembic/versions/*`，但工具消息、工具调用参数、资产引用和多轮 `ModelRequest` 都需要持久化结构。
   - 当前 `Message` 只有字符串 `content`，`ModelRequest` 只有一条请求状态；现有结构尚未覆盖 `assistant.tool_calls`、`tool` 消息、`tool_call_id`、每轮 usage 和重放游标。
   - 方案应明确新增 Alembic revision、旧数据默认值、回滚策略，并说明 `main.py` 当前通过 `Base.metadata.create_all` 初始化（`backend/app/main.py:77-82`）与生产迁移流程如何衔接。

2. **端到端 API 契约未定义**
   - `SendMessageRequest` 当前只有 `content/model/modality`（`backend/app/schemas/common.py:72-86`）。需要明确 `asset_ids`、文本/多模态 content parts、可选参数、工具开关和响应错误结构。
   - 图片生成与编辑应使用独立 schema，写清 `prompt/model/size/quality/n/response_format/asset_ids/mask_asset_id` 的约束、默认值和上限；不要继续复用文本请求 schema。
   - SSE 事件需给出版本化清单和 JSON 字段：至少包括 `message.created`、`message.delta`、`tool.started`、`tool.completed`、`image.created`、`message.completed`、`request.usage`、`error`，以及 `id`、重连和幂等语义。

3. **工具回合状态机未展开**
   - 需要定义：最多回合数、单回合最多工具数、参数校验失败、图片调用失败、用户停止、断线重连和重复执行时的状态转移。
   - `generate_image` 参数应使用 Pydantic 白名单模型；模型返回的任意字段、尺寸、数量和参考资产必须重新校验，并计入请求限额。
   - 每次工具调用需要唯一 `tool_call_id` 和幂等键。重连时应从数据库恢复已完成工具结果，避免重复扣费或生成重复资产。

4. **模型同步规则未定义**
   - 需指定管理员接口、请求超时、响应兼容形态（常见为 `data[].id` 或列表）、去重排序、原有手工模型的保留/删除规则和审计记录。
   - `/models` 通常只声明模型 ID，难以可靠推断文本、图片或编辑能力；需要渠道级能力配置或同步后的人工确认字段，不应仅凭名称分类。

### P1 建议补充

- 明确渠道模型唯一标识：仅用 `model` 会在多个渠道同名时产生歧义，建议内部使用 `channel_id + model`，前端展示名可保持简短。
- 明确错误码映射：认证失败、限流、超时、供应商 4xx、供应商 5xx、解析失败、资产校验失败分别映射稳定的内部错误码。
- 明确 usage 汇总口径：工具回合是每轮一条 `ModelRequest`，还是主请求聚合一条；输入/输出 token、图片计费字段和延迟如何展示给管理端。
- 明确取消和重试：POST 请求默认不自动重试；仅对连接建立失败或明确幂等的请求重试，并定义退避和总超时。
- 补充生产观测：渠道、模型、回合、状态、延迟、供应商 request id、错误码和响应大小的结构化日志，日志中禁止出现密钥、完整提示词和图片内容。

## 2. 技术选型评估

### 可行部分

- 继续使用 FastAPI、Pydantic、SQLAlchemy、httpx 和现有本地资产存储，符合项目基线，依赖变化小。
- 兼容聊天接口使用 SSE，图片编辑使用 multipart，都是覆盖面较好的协议边界。
- 现有渠道优先级路由和 Fernet 密钥存储可复用（`backend/app/services/models.py`、`backend/app/core/crypto.py`）。

### 需要调整的选型与边界

1. **Provider 层先做规范化适配器**
   - 当前 `openai_text` 仅返回文本 chunk/usage/request id，且固定拼接 `/chat/completions`（`backend/app/services/providers.py:26-62`）。建议引入内部 `TextRequest`、`StreamEvent`、`ToolCall`、`ImageResult` 类型，再由适配器处理供应商变体。
   - `temperature/top_p/max_tokens/reasoning_effort/response_format/tools/tool_choice` 应采用“可选且只发送已设置字段”，并设渠道能力开关；未知参数应避免静默发送到所有渠道。
   - SSE 解析应按 `data:` 帧增量合并 tool call 的 index、id、函数名和 arguments，同时处理空 delta、finish reason、usage 尾帧和非 JSON 错误帧。

2. **Base URL 策略必须统一**
   - 现有代码默认调用 `base_url + /chat/completions`、`base_url + /images/generations`（`providers.py:27,66`）。方案需规定管理员填写的是带版本前缀的 API 根，还是主机根；并在保存或运行时规范化，避免 `/v1/v1` 与漏掉版本前缀两类错误。
   - 模型同步、聊天、生成、编辑、响应接口的路径应配置化，不应假定所有渠道同时实现全部路径。

3. **同步 HTTP 的并发影响**
   - 当前聊天和图片请求使用同步 `httpx`；图片接口也在请求线程中等待完整响应（`workspace.py:452-495`）。短期可保留同步实现，但应设置 connect/read/write/pool 分项超时并限制响应大小；若启用多 worker 或长耗时图片任务，应迁移到 `AsyncClient` 或后台任务队列。

## 3. 实施可行性

### 现有基线确认

- 前端 `npm run build` 当前通过。
- 当前后端测试在 `TestClient` 启动阶段即失败：环境为 `fastapi 0.104.1 / starlette 0.27.0 / httpx 0.28.1`，Starlette 仍向 httpx 传入已移除的 `app` 参数。计划中的测试验收前应固定 `httpx<0.28`，或同步升级 FastAPI/Starlette，并将版本约束写入依赖文件。
- 当前上传接口只返回资产 ID 后即丢弃引用，前端 `uploadAttachment` 没有保存该 ID（`src/App.tsx:421-430`）；这与方案中的 `asset_ids` 目标存在直接断点。

### 推荐实施顺序

1. 先定稿内部请求/响应类型、错误码、SSE 事件和 Base URL 规则，增加 mock Provider。
2. 增加数据库 revision：消息元数据/工具字段、资产引用关系、请求回合和幂等约束；完成旧数据迁移。
3. 实现模型同步和渠道能力配置，再实现文本可选参数与普通流式请求。
4. 实现独立的图片生成/编辑服务：资产所有权校验、multipart、变体解析、结果保存。
5. 在已有普通文本流之上加入工具状态机和可恢复事件，不要把工具逻辑散落在 SSE 生成器中。
6. 最后接前端：资产预览/移除、编辑模式、模型筛选、工具/图片事件和错误状态。
7. 运行单元、契约、集成、构建和浏览器回归；补充真实渠道的脱敏联调记录。

## 4. 潜在风险与控制措施

| 风险 | 现状/触发条件 | 控制措施 |
| --- | --- | --- |
| 路径拼接错误 | Base URL 填写形态不统一 | 保存时规范化并在渠道测试中逐个验证最终 URL |
| SSRF | 管理端可配置任意 HTTP 地址；图片 URL 会被服务端再次抓取（`providers.py:73-76`） | 生产环境配置出站 allowlist；限制 scheme、解析后 IP、重定向、响应大小和 MIME；URL 下载默认关闭或仅允许渠道域名 |
| 资产越权/资源耗尽 | 资产输入尚未进入请求；data URL 和 multipart 可能放大内存 | 批量 ID 所有权查询、数量/总字节上限、MIME 实测、临时文件流式处理、过期清理 |
| 工具无限循环 | 文本模型可反复请求生图 | 最大回合/调用数、总耗时和额度；达到上限发出可重放错误事件 |
| 重连重复计费 | 当前流状态主要在进程内缓存（`workspace.py:20-47`） | 数据库记录每轮状态和幂等键；多 worker 部署使用共享状态存储或明确单 worker 限制 |
| 供应商响应差异 | tool call、usage、图片 URL/b64、错误格式存在变体 | mock fixture 覆盖每种变体；适配器返回统一内部类型，解析失败标记明确错误码 |
| 密钥与敏感数据泄漏 | 渠道测试、异常和请求日志可能记录 URL/头部/提示词 | 日志脱敏、异常只返回 request id 和内部错误码，前端不接触明文密钥 |
| 取消状态不一致 | `stop` 只更新数据库和内存标记，供应商请求未必立即终止 | 保存 cancel event，检查每个流/工具边界；为上游请求设置取消和最终状态收敛逻辑 |
| 前端模型歧义 | 同名模型来自多个渠道，且上传后没有引用状态 | 选项携带 channel id；显示已选资产、移除操作和上传失败；按事件类型更新消息而非只处理文本 delta |

## 5. 测试与验收门槛

### 必测用例

- `/models` 的多种响应结构、空列表、超时、鉴权失败和原有模型合并规则。
- Base URL 已带版本前缀、未带版本前缀、尾斜杠和自定义路径的最终请求 URL。
- 普通文本流、空 delta、usage 尾帧、tool call 分片合并、多个 tool call、参数 JSON 不完整和 finish reason。
- 工具成功、图片失败、文本二次请求失败、达到回合上限、停止、断线后重连和幂等重放。
- 生成 b64、URL、空 data、错误 MIME、过大响应；编辑 multipart、参考图/遮罩图和供应商 JSON 回退。回退必须是渠道显式能力，避免一次操作发送两次请求。
- 资产 ID 混用不同用户、已删除文件、超限数量/大小和非图片 MIME。
- 多 worker 或单 worker 的部署模式、迁移前后旧消息读取、管理审计和 usage 汇总。

### 通过标准

- `pytest -q`、`npm run build`、`python -m compileall` 均通过，依赖版本在锁定文件中可复现。
- mock Provider 契约测试覆盖上述响应变体；至少一条端到端链路验证模型同步 -> 选择模型 -> 文本流 -> 工具生图 -> 图片事件 -> 历史重放。
- 管理端可查看渠道能力、同步时间、失败原因和最后测试结果；用户端可完成参考图预览/移除/编辑并在刷新后保留消息与资产。
- 运行文档记录迁移命令、环境变量种子、出站网络策略、回滚步骤和已知供应商差异。

## 修订建议摘要

将当前方案标记为 v1 评估稿，新增“数据模型与迁移”“API/SSE 契约”“渠道能力与 Base URL”“工具状态机”“安全与出站网络”“重试/取消/幂等”“部署与回滚”七节；同步更新涉及文件清单，加入 Alembic revision、Provider mock fixtures、独立图片 schema、前端资产状态模块和依赖锁定变更。完成这些修订后，方案具备分阶段实施条件。
