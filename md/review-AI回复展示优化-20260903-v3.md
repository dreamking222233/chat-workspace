### P1-2：并发跨渠道重新生成时，来源请求 ID 与最终正文仍可能错配

**位置**

- `backend/app/api/workspace.py:661-678`
- `backend/app/api/workspace.py:803-810`
- `backend/app/api/workspace.py:1033-1045`
- `backend/app/api/workspace.py:1055-1063`
- `backend/app/api/workspace.py:1209-1220`

**问题**

`response_source_request_id` 只在根请求创建时写入并提交，后续 delta、成功完成和失败保存正文时只更新 `Message.content`，没有在同一事务中重新确认来源绑定。`idempotency_lock` 只覆盖请求准备与 `StreamingResponse` 创建，生成器实际执行前锁已经释放；多个标签页或直接 API 调用可以对同一 assistant 消息同时重新生成。

可出现以下顺序：Codex 请求 A 写入来源 A，官网版请求 B 随后写入来源 B，B 先结束，A 后结束并覆盖正文。最终正文来自 A，但来源仍为 B；读取和导出会把 Codex 的同形普通文本当作官网协议清洗，二次审查发现的误删路径再次成立。

**建议**

选择并落实明确的并发语义：要么对同一 assistant 消息只允许一个活动根请求；要么每次写入正文时在同一事务内写入对应来源请求 ID，并用版本号/当前请求条件阻止旧流覆盖新流。增加受控交错顺序的双向跨渠道并发回归。
