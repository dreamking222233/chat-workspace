# 文本模型兼容工具调用实施方案

日期：2026-09-02

## 用户原始需求

- 部分 OpenAI-compatible 文本模型不会返回原生 `tool_calls`。
- 系统需要通过 System Prompt 引导模型识别生图/图片编辑意图，并输出平台可解析的
  工具调用内容。
- 平台解析模型输出后调用现有图片模型，行为类似 Function Calling。

## 技术方案

1. 保留原生 OpenAI `tools/tool_choice`，同时增加平台级兼容协议，兼容原生工具能力
   缺失的渠道。
2. 文本请求启用图片工具时，在每轮 Provider 消息首部注入 System Prompt，约定模型
   仅在需要生图或编辑时输出：

   ```text
   <platform_tool_call>{"name":"generate_image","arguments":{...}}</platform_tool_call>
   ```

3. 新增增量解析器，支持标签跨 SSE chunk 拆分；普通文本继续流式输出，完整工具标签
   从用户可见内容中隐藏。
4. 工具标签严格解析为 JSON，只接收 `generate_image`，随后继续复用现有 Pydantic
   参数校验、资产归属校验、最大回合/调用数、图片 Provider、消息持久化与 SSE 事件。
5. 原生 `tool_calls` 优先；同一轮存在原生调用时不重复执行兼容标签。
6. 下一轮增加平台工具结果摘要，让不理解 `role=tool` 的文本渠道也能根据图片执行结果
   输出最终答复，避免重复请求同一工具。
7. 平台兼容调用使用保留 ID 前缀。第二轮仅把该类调用改写为普通
   `assistant/user` 上下文，避免不支持 `role=tool` 的网关返回 5xx；原生
   `tool_calls` 的消息结构保持不变。
8. 用户上传参考图时，在 Provider 用户消息中追加平台生成的附件元数据，使模型能把
   真实 `asset_ids`/`mask_asset_id` 写入编辑工具参数；服务端仍执行归属和文件校验。

## 涉及文件

- `backend/app/services/platform_tools.py`（新增）：协议常量、System Prompt、增量解析器。

- `backend/tests/test_platform_tools.py`（新增）：分片、普通文本、非法/完整标签测试。

## 风险与控制

- 标签被普通文本误触发：只解析完整起止标签和 JSON 对象，并对白名单工具再次校验。
- 标签分片泄露到界面：解析器保留最长标签前缀，确认是普通文本后才释放。
- 模型反复请求生图：继续使用现有最大回合和调用次数限制。
- Provider 同时返回原生与兼容调用：优先原生调用，避免重复生成和重复计费。
- 工具结果未被渠道理解：额外注入只含执行状态和资产引用的平台结果摘要。
- 渠道拒绝 OpenAI 工具消息回放：仅对平台保留 ID 的调用降级为普通消息，原生调用
  保持标准协议。
- 模型生成不受支持的图片尺寸：System Prompt 列出严格白名单，执行前继续由
  `GenerateImageToolArguments` 二次校验。
