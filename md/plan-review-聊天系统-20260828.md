# ChatGPT 对话系统计划评审

日期：2026-08-28

## 评审结论

方案整体可行，建议按阶段实施。现有 React/Vite 聊天页可以保留视觉层，通过 API hooks 和路由逐步替换本地状态；FastAPI + SQLAlchemy + MySQL 能覆盖认证、数据隔离、模型编排、导出和管理端需求。

## 检查结果

### 方案完整性

- 已覆盖注册登录、授权期限、项目/对话/消息、文本/图片模型、导出、使用记录和管理端。
- 已定义核心表、主要接口、前后端目录、分阶段任务和验收标准。
- token 统计以可空字段和原始 usage 预留，符合当前范围。

### 技术选型

- FastAPI、Pydantic、SQLAlchemy、Alembic 与 MySQL 组合适合 Python 后端和后续扩展。
- SSE 适合文本流式输出；图片生成使用任务状态和资源表，避免阻塞聊天请求。
- JWT、Argon2/bcrypt、RBAC、用户级数据过滤满足首期权限边界。

### 实施可行性

- 阶段拆分顺序正确：先认证和数据模型，再模型调用，最后图片、导出和管理端。
- 前端拆分保持 `src/styles.css` 和聊天布局不变，风险集中在状态管理、路由和 API 错误处理，范围可控。
- 首期可以使用本地文件存储和单一模型供应商，降低联调复杂度。

## 实施前补充建议

1. 首次编码前确定数据库运行方式（Docker Compose 或现有 MySQL），并固定迁移命令。
2. 先定义 OpenAPI schema 和错误码，再同时生成前端类型，减少前后端字段漂移。
3. 将模型 Provider、授权校验、用户数据过滤写成独立 Service，并为越权访问添加测试。
4. SSE 需要明确事件 ID、断线重连和停止生成接口；图片生成需要明确最大尺寸、超时和文件清理策略。
5. 生产部署前补充 refresh token 存储策略、CORS 白名单、限流和日志脱敏配置。

## 风险结论

- 未确定的模型供应商、token 来源和部署环境不会阻塞首期开发，计划中的适配器和可空 usage 字段已保留扩展点。
- 当前计划没有发现需要推翻技术路线的阻塞项；进入实施时按上述补充项建立默认配置即可。
