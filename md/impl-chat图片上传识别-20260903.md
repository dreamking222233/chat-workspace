## 1. 任务概述

为 `/chat` 的普通文本对话补齐图片视觉输入。用户仍先通过资产接口上传图片，发送文本时浏览器读取本地 `File`，按参考工作台的策略压缩成短期 JPEG/PNG Data URL，并通过 `media_inputs` 随文本请求提交。服务端只把资产 ID 和普通元数据写入消息，按渠道协议把像素挂到最后一条用户消息后转发给文本模型。

图片生成/编辑模式继续使用原有图片渠道和参考资产接口，不与文本视觉请求混用。

## 2. 核心实现

### 2.1 浏览器编码与交互

- `src/utils/mediaEncode.ts` 新增 `encodeVisionImageBlob`：原图 20 MiB 上限，最长边按 1600/1280/1024/800 阶梯缩放，JPEG 质量按 0.86/0.76/0.66 阶梯压缩，透明区域在 JPEG 输出时填白。
- 单张 Data URL 编码字符上限为 1,572,864；非 Canvas 环境保留合法 JPEG/PNG 的 FileReader 回退，并规范化 `image/jpg`。
- 根据模型 `supported_input_image_mime_types` 选择 JPEG 或 PNG 输出；前端保留宽高、MIME、字节数和 `detail` 元数据。
- `/chat` 上传控件改为支持多选，单轮最多 8 张；发送前阻止上传/编码进行中的提交，显示待发送缩略图，发送后在用户消息中显示带鉴权的资产缩略图。
- 文本模式上传提示“发送后将由文本模型读取”，不会进入图片生成接口；图片模式仍走原有参考图流程。

### 2.2 API 契约与服务端校验

- `TextMediaInput` 校验 Data URL 正则、Base64、JPEG/PNG 文件头、单张和整轮载荷大小、尺寸范围、MIME 一致性，并规范化资产 ID。
- `SendMessageRequest.media_inputs` 最多 8 项，并自动把媒体资产 ID 合并到 `asset_ids`；服务端再次校验资产属于当前用户且确为图片，拒绝文档资产、越权资产和未在消息附件列表中的视觉输入。
- `MessageResponse.asset_ids` 暴露历史附件 ID；数据库消息和 `ModelRequest.events_json` 不保存 Base64 像素。
- 文本渠道能力支持 `supports_input_image`、`max_input_images`、`input_image_max_bytes`、`input_image_detail` 和 `supported_input_image_mime_types`，可按渠道或模型覆盖。未配置 MIME 列表时默认 JPEG/PNG。
- 修正渠道能力映射的保留键处理，确保 `supported_input_image_mime_types`、`image_url_hosts` 等渠道级数组不会被误当作模型模态列表过滤。

### 2.3 Provider 协议适配

- `workspace._provider_messages` 仅在当前请求内把视觉 Data URL 附加到最后一条用户消息，并保留 `<platform_attachments>` 资产清单，后续图片工具仍可引用用户资产。
- Chat Completions 使用 `image_url` + `text` 内容部件。
- Responses 渠道使用 `input_image` + `input_text`，函数调用/工具结果继续转换为 `function_call` / `function_call_output`，并默认设置 `store: false`。
- 现有 SSE、工具调用、重连、幂等和图片生成流程保持不变；视觉像素不会进入持久化事件或图片生成接口。

## 6. 当前边界

- 当前渠道抽象是 OpenAI-compatible；已实现 Chat Completions 与 Responses 两种文本视觉形态。
- Data URL 只在本次请求内存中保留。历史消息仍保存资产 ID，若要再次把历史图片作为新的视觉上下文，需要从资产重新读取并重新编码。
- 图片上传仍受现有 `/assets/upload` 的文件类型和大小限制；文本视觉额外受单张/整轮编码及模型能力限制。
